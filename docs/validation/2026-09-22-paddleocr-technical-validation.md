# PaddleOCR PP-OCRv5 技术验证报告

**日期：** 2026-09-22

**结论：** 最短端到端技术验证通过，可以进入 PDF → TXT 正式实现
**说明：** 本报告验证本机兼容性、离线模型加载和基本链路，不等同于真实世界 PDF 的最终质量验收。

## 1. 验证目标

- 验证 MacBook Air M5、Apple Silicon、Python 3.12 能否运行 PaddleOCR。
- 固定使用 PP-OCRv5 mobile，不比较或接入 Tesseract。
- 验证模型可以显式保存到本地，转换阶段断网运行。
- 打通“扫描 PDF → PDFium 渲染 → PaddleOCR → UTF-8 TXT”。
- 初步记录速度、内存、旋转页和多页行为。
- 确认验证工作不影响 v1 功能和自动测试。

## 2. 验证环境

| 项目 | 结果 |
|---|---|
| 硬件 | MacBook Air M5，arm64 |
| 系统 | macOS 26.5.1 |
| Python | 3.12.13 |
| PaddlePaddle | 3.3.0，CPU |
| PaddleOCR | 3.7.0 |
| pypdfium2 | 5.13.0 |
| pdfplumber | 0.11.10 |
| 验证环境 | `/private/tmp` 下的独立虚拟环境，未修改 v1 `.venv` |

PaddlePaddle 自带的 CPU 运算检查通过，确认 Python 3.12 与 arm64 wheel 可以在本机运行。

## 3. 本地模型

使用 Paddle 官方模型源显式下载以下模型：

| 模型 | 用途 | 本地大小 |
|---|---|---:|
| `PP-OCRv5_mobile_det` | 文字区域检测 | 约 4.7 MB |
| `PP-OCRv5_mobile_rec` | 中文/英文文字识别 | 约 16 MB |
| `PP-LCNet_x1_0_doc_ori` | 0°/90°/180°/270°页面方向分类 | 约 6.6 MB |
| 合计 |  | 约 27 MB |

模型保存到显式本地目录。后续测试在无网络权限的环境运行，并同时传入模型名称与绝对模型目录，没有发生联网或再次下载。

重要发现：PaddleOCR 3.7.0 的默认检测模型已经不是 PP-OCRv5 mobile。只传模型目录会发生模型名称不匹配，因此正式代码必须同时固定模型名称和模型目录，不能依赖库的当前默认值。

## 4. 端到端结果

验证样例为本地合成的简体中文扫描 PDF，包含标题、段落、中文编号、英文、数字、列表和简单表格文字。页面以 200 DPI 渲染。

| 场景 | 页面 | 初始化 | OCR 推理 | 总耗时 | 平均置信度 | 峰值内存 |
|---|---:|---:|---:|---:|---:|---:|
| 正常方向扫描页 | 1 | 0.60 秒 | 2.97 秒 | 3.60 秒 | 0.914 | 约 2.72 GB |
| 旋转 90° 扫描页 | 1 | 0.61 秒 | 3.06 秒 | 3.70 秒 | 0.988 | 约 2.75 GB |
| 相同样例 5 页 | 5 | 0.61 秒 | 14.31 秒 | 15.05 秒 | 0.914 | 约 2.77 GB |

结果说明：

- 正常页和旋转页的可见文字均被识别，输出为 UTF-8 TXT。
- OCR 会调整部分空格，例如 `中文 OCR` 可能变为 `中文OCR`；列表编号后的空格也可能消失，需要文本清理层处理。
- 简单表格的各单元格能够识别，但被输出为多行，不能仅靠 OCR 自动恢复为制表符表格，仍需要坐标布局层。
- 不启用页面方向分类时，90° 页面平均置信度约 0.431，输出基本不可用；启用后恢复正常。因此方向分类模型属于必需依赖，不是可选增强。
- 单进程连续处理 5 页时内存没有随页数明显增长，但基础峰值较高。

## 5. 性能与资源结论

- 当前验证环境约 875 MB；其中包含 PaddleOCR/PaddleX、OpenCV 等完整依赖。模型另占约 27 MB。
- 依赖体积较大，但当前不做安装包，因此不构成阶段阻塞。
- OCR 峰值内存约 2.0–2.8 GB。正式版默认应只运行一个 OCR 任务，批量文件按页串行处理，不能按上传文件数直接并发。
- 模型对象应在一次批处理内复用，避免每页重复初始化。
- 页面图像应设置 DPI、最大像素数和及时释放策略，防止超大页面推高内存。

## 6. 验证中发现的边界

1. **置信度不能单独代表质量。** 一个经过较强 JPEG 压缩的测试 PDF 出现漏字，但模型仍给出较高置信度。正式报告可以显示置信度，但不能把它当作唯一成功标准。
2. **PDF 生成问题无法由 OCR 修复。** 使用受限字体环境生成的一份测试 PDF 在渲染时已经丢失中文 glyph，OCR 只能识别页面实际可见内容。该文件不计入 OCR 质量结论。
3. **阅读顺序仍需单独实现。** PaddleOCR 提供文字框与识别结果，但双栏、表格、页眉页脚和跨页段落需要本项目自己的布局规则。
4. **运行时必须显式离线。** 正式代码要检查三个本地模型目录，缺失时给出初始化说明；转换路径不允许自动访问模型站点。
5. **PaddleOCR 版本必须锁定。** 上游默认模型已经发生变化，升级依赖前需要重新验证 API、模型名称、输出 JSON 和资源占用。

## 7. 对正式实现的约束

- 固定 PaddlePaddle 3.3.x、PaddleOCR 3.7.x 的已验证范围，具体锁定版本在依赖接入时确定。
- 明确配置 `PADDLE_PDX_CACHE_HOME`，不把模型隐式写入用户主目录。
- 使用 `PP-OCRv5_mobile_det`、`PP-OCRv5_mobile_rec` 和 `PP-LCNet_x1_0_doc_ori` 的显式路径。
- 文本型 PDF 优先原生提取；扫描页或原生提取质量异常的页面才进入 OCR。
- OCR 单任务运行，页面串行处理，加入超时、取消、页数与像素限制。
- 输出层负责空格、段落、列表、表格降级和页面间分隔，不直接拼接未经处理的 `rec_texts`。
- 转换报告记录 OCR 页数、方向校正、低质量警告、耗时和可能丢失的版面。

## 8. 尚未完成的质量验收

正式实现阶段仍需使用真实 PDF 覆盖：

- 150 DPI、300 DPI、模糊、倾斜和带噪声扫描件。
- 中文双栏、页眉页脚、脚注和跨页段落。
- 有框表格、无框表格和跨页表格。
- 文本页与扫描页混合的 PDF。
- 加密、损坏、超大和恶意构造的 PDF。

以上属于实现与质量加固，不影响本次“技术链路可行”的结论。
